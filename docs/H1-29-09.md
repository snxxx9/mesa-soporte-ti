## 1. Problema

La organización recibe solicitudes de soporte informático por distintos medios y no cuenta con un registro centralizado. Esto dificulta saber qué solicitudes están pendientes, quién es responsable de atenderlas y cuál es su prioridad y estado

## 2. Objetivo

Desarrollar una aplicación web que permita registrar y organizar las solicitudes de soporte informático, asignar un responsable y consultar su prioridad y estado desde su creación hasta su cierre

## 3. Alcance v0.1

### Incluido

- Registrar solicitante, título, descripción, categoría y prioridad.
- Generar un identificador único y fecha de creación para cada solicitud.
- Listar solicitudes con estado, prioridad y responsable.
- Consultar una solicitud y actualizar responsable y estado.
- Usar los estados Nuevo, En proceso, Resuelto y Cerrado.
- Filtrar por estado, prioridad o categoría.
- Mostrar el total de solicitudes y la cantidad por estado.
- Guardar usuarios/responsables, tickets, categorías e historial de cambios relevantes en SQLite.
- Validar entradas, manejar errores y conservar pruebas funcionales e integración.
- Mantener repositorio Git y tablero GitHub Projects con evidencias por hito.

### Fuera del alcance inicial

Aplicación móvil nativa, chat, archivos adjuntos, envío automático de correos, pagos, integración con otros sistemas y despliegue público en internet. Tampoco se incluye autenticación ni permisos por perfil en esta versión: los usuarios/responsables se usarán como registros de referencia en una demostración local con datos ficticios.

Estas exclusiones son decisiones propuestas por el equipo para mantener el proyecto pequeño, no prohibiciones del profesor. Si el docente exige una función adicional, se registrará el cambio y se revisará el plan.

## 7. Modelo de datos conceptual

Se proponen cuatro grupos de datos:

| Entidad | Qué representa | Datos iniciales |
|---|---|---|
| Usuario | Personas que solicitan o atienden soporte. | Identificador, nombre, habilitado para atender. |
| Ticket | Una solicitud de soporte. | Identificador, título, descripción, fecha, prioridad, estado, solicitante, responsable opcional, categoría. |
| Categoría | Clasificación del problema. | Identificador y nombre. |
| Cambio de ticket | Registro de una modificación relevante. | Identificador, ticket, fecha, campo, valor anterior y valor nuevo. |

Relaciones: un usuario puede solicitar muchos tickets; un usuario habilitado puede ser responsable de muchos tickets; cada ticket tiene un solicitante, cero o un responsable y una categoría; una categoría reúne muchos tickets; un ticket puede tener muchos cambios.

El solicitante se seleccionará de usuarios de prueba precargados. Esto evita crear administración de usuarios o autenticación para el MVP. El script físico, restricciones y diagrama ER detallado corresponden a H2. Sin autenticación no se afirmará que el historial prueba la identidad de quien operó la aplicación.

## 8. Interfaz y arquitectura inicial

El archivo `BOCETOS.html` muestra tres pantallas estáticas de ejemplo:

1. **Listado y resumen:** total, conteo por estado, filtros y lista de tickets.
2. **Nueva solicitud:** formulario con los cinco datos exigidos.
3. **Detalle:** datos del ticket, responsable, estado e historial de cambios.

Flujo técnico propuesto: **navegador → aplicación Python/Flask → SQLite**. El navegador muestra HTML/CSS y envía formularios; Flask valida, consulta y actualiza; SQLite conserva datos en un archivo. Las consultas usarán parámetros y las relaciones se validarán.

Justificación preliminar: permite concentrarse en el flujo solicitado, utiliza una base relacional sin administrar un servidor separado y reduce las piezas que deben instalarse. La decisión requiere la revisión cruzada del equipo en H2.
